## Scope and authority

Persistence implements the settled authority model (I12–I14, C2):

| Authority | Rule |
|---|---|
| Current workflow state and lifecycle | Stored directly in SQLite columns; **not** reconstructed by journal replay |
| Stored graph snapshot | Immutable per run after creation |
| Activity journal | Append-only, ordered, explanatory; **not** a second write authority |
| Provider registrations | Machine-local catalog rows with monotonic `config_revision` |
| JSON/JSONL export | Read-only inspection snapshot; **never** a competing write path |

Rejected patterns for MVP:

- event sourcing or replay reducers for current state;
- ORM layers that hide transaction boundaries;
- dual authority between SQLite and export files;
- holding a SQLite write transaction or write lock across provider subprocess execution.

Integration-owned persistence-record DTOs map to core model types at the capability boundary ([architecture.md](architecture.md) § Boundary data). Core does not import SQLite.

## Operator recovery guidance

Engine stores authority in one `{state_root}/state.db`; its location and permissions are defined in [configuration.md](configuration.md). Do not edit this file while `loop-engine` is running. For backup, stop all invocations and copy complete `LOOP_ENGINE_HOME`, preserving SQLite companion `-wal`/`-shm` files, integration metadata, ownership, and permissions. Restore complete home into a private replacement directory; never combine database and metadata from different homes. No backup, restore, repair, delete, replay, or import command is exposed. JSON output, exports, and operational traces are inspection aids, not restorable authority. Step-by-step procedures and symptom actions are in [operator-guide.md](operator-guide.md#backup-and-recovery).

Every normal invocation validates migration version and v1 schema before dispatch. A newer-version, malformed, or corrupt store fails closed. Preserve database unchanged for diagnosis; select fresh `LOOP_ENGINE_HOME` only when intentionally starting independent empty installation. Never decrement schema metadata, edit DDL, or replace/regenerate `integration_metadata.integrity_key` independently of database because cursors and disable acknowledgements are bound to it.

All 21 catalog operations are callable. Operation rows below define active persistence semantics; use `loop-engine --list-operations` for authoritative argv templates.

## Database identity and open lifecycle

Exactly one SQLite database file per machine-local installation: `{state_root}/state.db` per [configuration.md](configuration.md). There is no shard path, alternate store selector, or project-selected database identity.

Open sequence on every CLI invocation that needs persistence:

1. Open `state.db` with bundled SQLite through `rusqlite` (read/write, create-if-needed only when an owning operation may initialize an empty store).
2. Apply connection-local `busy_timeout` from `sqlite_busy_timeout_ms`.
3. Run the serialized startup schema pipeline ([migration policy](#migration-policy)): under an immediate writer lock, read `user_version`, reject databases whose applied schema version exceeds the binary's supported version ([schema-version compatibility](#schema-version-compatibility)), apply pending forward-only migrations, and verify bundled v1 schema shape — **before** any write-affecting connection pragma.
4. Apply persisted [connection pragmas](#connection-pragmas) (`foreign_keys`, `journal_mode=WAL`, `synchronous`, `temp_store`).
5. Verify integration metadata and serve operation requests through short read or write transactions per [transaction boundaries](#transaction-boundaries).

Startup migration failure is a pre-dispatch persistence error: no application operation runs, no provider subprocess starts, and no partial migration version is recorded.

## Connection pragmas

Apply persisted pragmas on every connection only **after** the [startup schema pipeline](#migration-policy) succeeds (future-version rejection and migration/postcheck complete). Connection-local `busy_timeout` is applied immediately after open (step 2 above).

| Pragma | Value | Purpose |
|---|---|---|
| `foreign_keys` | `ON` | Enforce referential integrity for catalog/run/journal associations |
| `journal_mode` | `WAL` | Concurrent readers with one writer; append workload with checkpoint recovery (**write-affecting**; must not run before future-version rejection) |
| `synchronous` | `FULL` | Acknowledged commits are durable across process crash and power loss |
| `busy_timeout` | `sqlite_busy_timeout_ms` | Bounded wait on `SQLITE_BUSY` before surfacing persistence failure ([cli-contract.md](cli-contract.md#resource-bounds-d008), T008) |
| `temp_store` | `MEMORY` | Keep small temp structures off disk for short transactions |

`busy_timeout` is set from the `sqlite_busy_timeout_ms` bound on every connection for its lifetime. Integrations **MUST NOT** disable foreign keys, downgrade to rollback journal mode, or set `synchronous = OFF` in production paths.

### Acknowledged-commit durability

With `journal_mode=WAL` and `synchronous=FULL`, a successful `COMMIT` means the transaction is on stable storage before the call returns: acknowledged state and journal mutations survive process crash and power loss. This contract does **not** claim durability for transactions that never reach successful `COMMIT`, for connections that fail before `COMMIT` completes, or for outcomes inferred without [authoritative verification](#commit-outcome-verification) after commit I/O failure.

## Busy and locking policy

SQLite writer serialization is the cross-process linearization primitive. Policy:

| Rule | Requirement |
|---|---|
| Provider isolation | **No** write transaction, `BEGIN IMMEDIATE`, or application-level write lock is held while a provider subprocess runs |
| Read-before-provider | Load authoritative snapshot with read-only queries or a read transaction that ends before provider spawn |
| Write-after-provider | Open write transaction only after provider returns (or after provider-free decision is finalized in memory) |
| Transaction size | One write transaction per durable mutation command; no multi-operation application batching |
| Busy handling | Rely on `sqlite_busy_timeout_ms`; on exhaustion return persistence operation error without claiming partial commit |
| Cross-process overlap | Accidental concurrent CLI processes serialize on SQLite; correctness comes from CAS checks inside write transactions, not caller tokens (I36) |

WAL allows concurrent readers during a writer transaction. Writers still serialize; create-versus-catalog races resolve by commit order plus semantic rechecks below.

## Migration policy

Migrations are forward-only, ordered, and transactional. Integration uses `rusqlite_migration` with SQL files under `crates/loop-engine-integrations/migrations/`.

| Rule | Behavior |
|---|---|
| Ordering | Numeric prefix order (`0001_initial.sql`, `0002_…`, …); each file is one migration version |
| Application | Each pending migration runs inside a single SQLite transaction; success records version, failure rolls back that migration entirely |
| Exactly-once | Concurrent opens may race migration; `rusqlite_migration` version table ensures each migration applies at most once |
| Empty store | First open on empty file applies all bundled migrations and yields supported schema |
| Downgrade | **Forbidden** — older binaries **MUST NOT** open newer databases |
| Dual-write | **Forbidden** — no parallel JSON/TOML authority or shadow tables for the same facts |

### Schema-version compatibility

| Condition | Behavior |
|---|---|
| Applied version `<` binary supported version | Apply pending migrations at open |
| Applied version `=` binary supported version | Open normally |
| Applied version `>` binary supported version | Fail open with persistence error naming supported and observed versions; no reads or writes; rejection occurs inside the startup schema pipeline before write-affecting pragmas |

MVP ships one supported schema generation (`0001`, published by T105). Export and CLI envelope schema versions are independent integers ([cli-contract.md](cli-contract.md), D015).

At the supported version, open **MUST** verify each bundled v1 table and index by comparing live `sqlite_master.sql` to the authoritative shape derived from `0001_initial.sql` (not names alone). Deterministic mismatches classify as missing objects or SQL divergence.

### Migration `0001` schema (T105)

**Status:** Published by T105. Canonical DDL: `crates/loop-engine-integrations/migrations/0001_initial.sql`. Frozen table/column/index reference: [persistence-schema.md](persistence-schema.md).

Migration `0001` materializes every semantic branch required by this contract:

- `integration_metadata` with one 32-byte `integrity_key` row initialized via `randomblob(32)` ([Integration integrity key](#integration-integrity-key));
- `provider_registrations` with monotonic `config_revision`, enabled/tombstoned status, partial unique enabled handle index, and executable/argv/CWD/timeout columns;
- `runs` binding `(registration_id, config_revision_at_create)` plus authoritative workflow/lifecycle/version/label columns, immutable canonical graph projection, graph revision, and frozen inputs;
- append-only `evidence` with stable run-scoped IDs;
- append-only `journal_entries` with unique `(run_id, sequence)`, denormalized `outcome`, and full journal-contract wire payload;
- `run_journal_sequences` for atomic per-run sequence allocation in the same write transaction as journal insert;
- `evidence_associations` linking journal sequences to evidence rows for attempt commits;
- indexes for active runs by registration, catalog/history/evidence ordering, and catalog pagination;
- `ON DELETE RESTRICT` on all run-scoped foreign keys and no run-delete path (I45).

Journal entry payload encoding is T011; this document freezes transactional semantics. Column-level authority and mutability are frozen in [persistence-schema.md](persistence-schema.md).

## Integration integrity key

Pagination cursors (cursor v1) and `provider.disable` acknowledgement tokens are integration-owned, keyed authenticators. They are **not** caller authority, configuration secrets, or server-side session leases.

| Rule | Requirement |
|---|---|
| Storage | One row in internal `integration_metadata` keyed `integrity_key` holding exactly 32 bytes |
| Initialization | Migration `0001` (or first migration touching metadata) inserts the row with `randomblob(32)` when absent; key is created once per database |
| Lifetime | Persists across process invocations and CLI restarts until database deletion; **MUST NOT** rotate automatically in MVP |
| Algorithm | HMAC-SHA-256 using the approved `sha2` SHA-256 primitive (standard HMAC construction) |
| Domain separation | Distinct UTF-8 domain labels per artifact kind ([cli-contract.md](cli-contract.md) § Integrity MAC (cursor v1), § Disable acknowledgement token wire form); cursor and disable-ack tags are not interchangeable |
| Verification | Constant-time MAC compare before using payload fields (`last_key`, digests, registration binding) |
| Exposure | **MUST NOT** appear in CLI stdout/stderr, operational trace, export artifacts, configuration files, or provider handoff |
| Caller/config authority | **Forbidden** — no TOML key, environment override, or argv-supplied MAC secret |

### Key lifecycle and failure modes

| Condition | Behavior |
|---|---|
| Empty store first open | Migration creates `integrity_key`; subsequent opens load it |
| Row missing after migrations | Open fails with `persistence.failed`; no application dispatch |
| Row present but length ≠ 32 bytes | Open fails with `persistence.failed` |
| Same-user SQLite tampering of `integrity_key` or metadata row | Store corruption → open or verify failure (`persistence.failed` / `cursor.invalid` / `catalog.ack_token.invalid`); **not** an authorization bypass — valid tags cannot be forged without the stored key |
| MAC verification failure on cursor or ack token | Domain rejection (`cursor.invalid` or `catalog.ack_token.invalid`); **MUST NOT** treat as stale catalog state |

Integrity protection preserves the stateless pagination model: cursors remain opaque wire values with no server-side session table, lease, or external service.

## Internal version and sequence fields

| Field | Scope | Increments when | Used for |
|---|---|---|---|
| `config_revision` | registration | `provider.add` (initial `1`), `provider.update`, `provider.disable`, `provider.restore` | Run-creation recheck; provider `config_revision` handoff; disable `ack_token` binding |
| `workflow_state_version` | run | Workflow state ID changes on accepted transition | Post-provider transition CAS |
| `lifecycle_version` | run | Lifecycle changes (`active` → `final` or `terminated`) | Post-provider transition and lifecycle CAS |
| `label_version` | run | `run.label` while active | Label freshness only; **does not** participate in gate CAS |
| `journal.sequence` | run | Every journal insert for that run | Ordering and correction links; allocated inside the same write transaction as the insert |

Label, note (`run.annotate`), and evidence (`run.evidence.add`) mutations **MUST NOT** increment `workflow_state_version` or `lifecycle_version` (I36). Gate evaluation CAS compares only `(workflow_state_version, lifecycle_version)` observed at snapshot load.

## No write lock across provider

State-changing provider flow ([architecture.md](architecture.md) § State-changing operation flow):

```text
1. BEGIN read snapshot (or autocommit SELECTs) → load run, graph, versions, evidence selection
2. END read phase — connection must not hold a write transaction
3. Invoke provider subprocess (unbounded wall-clock; may exceed `sqlite_busy_timeout_ms` safely)
4. Core decides outcome from stored graph + observed provider result
5. BEGIN IMMEDIATE write transaction
6. CAS + journal/state mutations
7. COMMIT or ROLLBACK
```

Steps 1–4 apply to `run.create` (`describe` / `validate_inputs`), `run.request` (`evaluate_gates`), `run.guidance`, `run.compatibility`, and `provider.check` provider phases.

Provider-free operations skip step 3 but still use short write transactions for mutations.

## Transaction boundaries

One SQLite write transaction per durable command unless noted read-only.

| Operation class | Provider phase | Write transaction contents |
|---|---|---|
| `provider.add` | none | Insert registration `config_revision = 1`; enforce handle uniqueness |
| `provider.update` | none | Compute active-set digest; increment `config_revision`; replace executable/argv/CWD/timeout atomically |
| `provider.rename` | none | Handle change only; `config_revision` unchanged |
| `provider.disable` (warning pages) | none | **Read-only** pagination of affected runs; each cursor MAC-verified; final page mints HMAC `ack_token` binding `registration_id`, `config_revision`, `active_set_digest`, and completed `warning_traversal_digest` |
| `provider.disable` (`--allow-active-runs`) | none | Verify disable-ack MAC and token binding (registration, `config_revision`, `active_set_digest`, `warning_traversal_digest`); recompute digest; tombstone; increment `config_revision` |
| `provider.restore` | none | Re-enable tombstoned ID; set fields; increment `config_revision`; handle uniqueness |
| `run.create` | `describe` (+ optional `validate_inputs`) | After provider success: recheck enabled registration and `config_revision`; insert run, snapshot, inputs, initial versions, creation journal |
| `run.evidence.add` | none | Insert evidence; append mandatory journal entry; **no** workflow version bump |
| `run.annotate` | none | Append journal entry; **no** workflow version bump |
| `run.label` | none | One `BEGIN IMMEDIATE` write transaction: re-read `lifecycle`; if `active`, update label + `label_version` and append `label.changed` completed; if `final` or `terminated`, preserve label and append `label.changed` rejected (`run.lifecycle.terminal`); **no** workflow/lifecycle version bump |
| `run.request` (gate-free) | none | One `BEGIN IMMEDIATE` write transaction linearizes re-read, event resolution, `(workflow_state_version, lifecycle_version)` CAS when any state change is attempted, and journal append |
| `run.request` (gated) | `evaluate_gates` | Post-provider CAS on `(workflow_state_version, lifecycle_version)`; transition or stale/error attempt |
| `run.guidance` | `live_guidance` | Journal guidance attempt; no state/version change |
| `run.compatibility` | `check_compatibility` | Journal compatibility attempt; no state/version change |
| `run.terminate` | none | Lifecycle update + journal; bumps `lifecycle_version` |
| `run.export` | none | **Read-only** consistent snapshot (SQLite snapshot isolation or single read transaction) |
| Reads (`run.show`, `run.history`, …) | none | Read-only |

Catalog mutations never append per-run journal entries (I40). Rejected or errored `run.create` produces **no** run row and **no** run journal.

## Workflow CAS (post-provider)

For gated `run.request` and any mutation that applies a provider verdict to workflow state:

1. Snapshot records `expected_workflow_state_version` and `expected_lifecycle_version` during step 1 of [no write lock across provider](#no-write-lock-across-provider).
2. After provider returns and core accepts a transition candidate, the write transaction:
   - reads current versions from the `runs` row;
   - if either version differs → **stale branch** (below);
   - else applies state/lifecycle updates, increments the bumped version(s), inserts journal with outcome `completed` or `rejected`, and commits.

Gate-free `run.request` skips provider invocation but **MUST NOT** split authoritative read, resolve, and mutate across transactions. When persistence applies any workflow or lifecycle change, the write transaction re-reads the run row, resolves the event against the stored graph, compares `(workflow_state_version, lifecycle_version)` to the values observed at resolution time, applies updates only on match, increments bumped version(s), and appends the journal attempt in the same transaction. Concurrent gate-free transitions therefore use the same version CAS as gated paths; only the provider phase differs. Rejection-only paths (unknown event, terminal lifecycle denial, graph incompatibility without state advance) append journal without version bump inside one write transaction.

### Stale evaluation branch

When post-provider versions do not match the snapshot:

- **MUST NOT** change workflow state or lifecycle;
- **MUST** append one journal entry with outcome class operation error and reason `state.stale_version` when persistence remains available;
- **MAY** include provider observations in the attempt record when provider ran;
- commit atomically (journal-only mutation inside the write transaction).

This satisfies I11 (no silent advance), I36 (stale never transitions), and I35 (attempt journalable after run lookup).

## Registration-config CAS (`run.create`)

Before any provider call:

1. Resolve enabled registration and `config_revision` into immutable `registration` handoff ([provider-protocol-v1.md](provider-protocol-v1.md)).
2. Record `resolved_config_revision` for the creation attempt.

After provider graph validation succeeds, immediately before insert:

1. `BEGIN IMMEDIATE` write transaction.
2. Re-read registration row: still enabled and `config_revision == resolved_config_revision`.
3. If check fails → `provider.registration.stale` operation error; **ROLLBACK**; no run row; no run journal.
4. Else insert run bound to `(registration_id, config_revision)`; graph snapshot; inputs; initial versions; creation journal; `COMMIT`.

Creation-time executable digest drift without matching `config_revision` is rejected before persistence ([provider-protocol-v1.md](provider-protocol-v1.md)); persistence recheck covers catalog mutations during provider work.

### Stale create narratives

| Interleaving | Result |
|---|---|
| `provider.update` / `disable` / `restore` commits before create write | Create recheck fails → `provider.registration.stale`; no run/journal |
| Create commits first | Later catalog mutation sees new run in active-set digest |
| `provider.rename` during create | `config_revision` unchanged → create may succeed if still enabled |
| Registration tombstoned during create provider phase | Create recheck fails → `provider.registration.stale` |

## Catalog mutation: affected active-set digest

For `provider.update`, `provider.disable`, and `provider.restore`, the write transaction:

1. Computes `active_set_digest` = SHA-256 hex over UTF-8 canonical JSON array of **sorted** active run IDs (`lifecycle = active`) for the target `registration_id`. Empty set hashes `[]`.
2. Applies the catalog mutation and `config_revision` increment in the **same** transaction as digest computation (digest reflects pre-mutation active set for disable warning flow; see below).

`provider.update` returns affected count and paginated impact link; no acknowledgement token.

### Disable acknowledgement guard

Warning pagination (`provider.disable` without `--allow-active-runs`):

- read-only queries only;
- each `--warning-cursor` **MUST** verify cursor v1 MAC and `warning_traversal_digest` chain before continuing;
- only the **final** page (no `next_cursor`) mints an HMAC-protected `ack_token` binding `registration_id`, `config_revision`, `active_set_digest`, and `warning_traversal_digest` for the completed warning traversal ([cli-contract.md](cli-contract.md) § Disable acknowledgement token wire form).

Authorized disable (`--allow-active-runs <ACK-TOKEN>`):

1. `BEGIN IMMEDIATE` write transaction.
2. Decode token wire; constant-time verify disable-ack MAC.
3. Verify `token_kind = provider.disable_ack` and registration ID matches target.
4. Recompute current `active_set_digest` and `config_revision`.
5. If either differs from token binding → reject with `catalog.ack_token.stale`; **ROLLBACK**.
6. Recompute `warning_traversal_digest` for the current active set; if it differs from token binding → reject with `catalog.ack_token.stale`; **ROLLBACK**.
7. Else tombstone registration, increment `config_revision`, `COMMIT`.

First/intermediate warning cursors, edited or skipped pages, MAC failures, caller-supplied digests without a valid final-page token, or tokens missing completed traversal binding **MUST** reject (`cursor.invalid`, `catalog.ack_token.invalid`, or `catalog.ack_token.stale` as applicable).

## Create versus catalog writer linearization

SQLite orders concurrent writers; application semantics must be correct for **both** orders without caller coordination.

| Order | Create path | Catalog mutation path |
|---|---|---|
| **Catalog first** | Create recheck sees new `config_revision` → `provider.registration.stale` | Succeeds; digest/count include only runs existing at commit |
| **Create first** | Inserts run bound to observed `config_revision` | Succeeds; post-create active set includes new run in subsequent digest/count |

Neither order may produce partial run without journal or torn catalog row. `BEGIN IMMEDIATE` ensures the second writer blocks until the first completes; rechecks handle logical conflicts.

## Label, note, and evidence concurrency

### `run.label` serialized write transaction

`run.label` is provider-free. After successful run lookup, persistence **MUST** open one `BEGIN IMMEDIATE` write transaction that:

1. Re-reads the authoritative `runs` row (`lifecycle`, current label, `label_version`). **MUST NOT** read or compare `workflow_state_version` or `lifecycle_version` for CAS (I36).
2. If `lifecycle = active`: apply the requested label change; increment `label_version`; append `label.changed` with outcome `completed` in the same transaction.
3. If `lifecycle` is `final` or `terminated`: **MUST NOT** change the stored label or `label_version`; append one `label.changed` entry with outcome `rejected` and reason `run.lifecycle.terminal` in the same transaction (I35, I41).
4. `COMMIT` atomically (label + journal on success; journal-only on terminal rejection).

Pre-lookup lifecycle observation is not authoritative. Concurrent lifecycle commits may interleave between lookup and write; correctness depends on the in-transaction re-read.

### Concurrent non-label mutations

| Mutation | Workflow CAS | Concurrent gated `run.request` |
|---|---|---|
| `run.annotate` | Does not read or bump workflow/lifecycle versions | In-flight evaluation uses pre-annotation snapshot; commit still succeeds if versions unchanged |
| `run.evidence.add` | Same | Same |

Writer order when annotation or evidence append races an active-lifecycle transition commit:

- **Append first** → transition CAS unaffected; transition may proceed.
- **Transition first** (lifecycle still `active`) → append applies to current state; no invalidation of already-committed transition.

### `run.label` vs `run.request` final transition

Applies when the request commits a workflow transition into a final lifecycle state (`lifecycle` becomes `final`).

| Order | Final transition path | `run.label` path | Outcome |
|---|---|---|---|
| **Label first** | CAS succeeds; `lifecycle` becomes `final` | Re-read sees `active`; label update succeeds | Both commit; label change durable from first transaction |
| **Transition first** | CAS succeeds; `lifecycle` becomes `final` | Re-read sees `final`; label preserved; `label.changed` rejected `run.lifecycle.terminal` | Transition committed; label unchanged; rejection journaled |

When `run.request` commits while lifecycle remains `active` (non-final state change or rejection-only path), `run.label` re-read still sees `active` and may succeed in either order. Label changes **MUST NOT** invalidate in-flight gate evaluation (I36).

### `run.label` vs `run.terminate`

| Order | `run.terminate` path | `run.label` path | Outcome |
|---|---|---|---|
| **Label first** | `lifecycle` becomes `terminated` | Re-read sees `active`; label update succeeds | Both commit; label change durable from first transaction |
| **Terminate first** | `lifecycle` becomes `terminated` | Re-read sees `terminated`; label preserved; `label.changed` rejected `run.lifecycle.terminal` | Termination committed; label unchanged; rejection journaled |

Repeated termination rejection on `run.terminate` follows its own journal rule; `run.label` races only with the first successful termination commit.

Evidence appended during provider execution is visible only if committed before snapshot load; otherwise subsequent requests pick it up. No automatic mid-flight snapshot refresh.

## Attempt journaling (rejections, errors, and provider-advisory paths)

After successful run lookup, syntactically valid `run.request`, `run.guidance`, and `run.compatibility` attempts that do not change workflow state, and provider-advisory operations with rejected or errored outcomes, **MUST** append a durable journal entry when persistence is available (I35):

| Case | Provider | State change | Journal |
|---|---|---|---|
| Unknown event | none | none | Rejection attempt appended |
| Terminal lifecycle denial (`run.request`) | none | none | Rejection attempt appended |
| Terminal label change (`run.label`) | none | none | `label.changed` rejection `run.lifecycle.terminal` appended |
| Failed gate | `evaluate_gates` | none | Rejection attempt with verdicts |
| Stale version after gates | `evaluate_gates` | none | Error attempt `state.stale_version` |
| Inline evidence ID already exists for run | any already completed provider work remains observed | none | Rejection attempt `evidence.invalid`, with no evidence claims |
| Provider evidence ID already exists for run | `evaluate_gates` | none | Error attempt `provider.evidence.malformed`, preserving provider observation and valid verdict facts but making no evidence claims |
| Guidance rejected or errored (including terminal denial) | `live_guidance` or none | none | Attempt appended |
| Compatibility rejected or errored (including terminal denial) | `check_compatibility` or none | none | Attempt appended |

Inline evidence, selected-evidence associations, and valid provider evidence **MUST** commit in the same transaction as the attempt record (I14, I35). After authoritative version selection and while holding the same SQLite write lock, persistence **MUST** check proposed inline and provider evidence IDs against existing run evidence before insertion. A collision selects the matching no-mutation journal disposition above; it **MUST NOT** escape as an unjournaled primary-key error. Provider collisions take precedence when one attempt contains both provider and inline collisions. Stale-version disposition takes precedence over evidence collision because stale attempts claim no evidence.

## SQLite constraint mapping

Integration maps **expected** `SQLITE_CONSTRAINT` failures from schema-enforced invariants to frozen domain rejection codes in [operation-catalog.md](operation-catalog.md) § Outcome and reason taxonomy. **Unexpected** constraint failures, `SQLITE_CORRUPT`, `SQLITE_NOTADB`, and other integrity errors map to `persistence.failed` (operation error); callers **MUST NOT** treat them as domain rejections.

| Schema enforcement | Operation context | Reason code |
|---|---|---|
| Unique enabled provider handle | `provider.add`, `provider.rename` | `catalog.handle.duplicate` |
| Unique enabled provider handle on restore | `provider.restore` | `catalog.handle.occupied` |
| Unique evidence ID per run | `run.evidence.add` | `evidence.invalid` |
| Unique journal `(run_id, sequence)` | any journal insert | `persistence.failed` (unexpected race or logic defect) |

When constraint context is ambiguous or indicates corruption, use `persistence.failed`.

## Commit outcome verification

After commit I/O failure, the failing connection's transaction state is **unknown**. Integrations **MUST NOT** infer rollback, unchanged state, or successful mutation from driver teardown alone.

Verification procedure:

1. Close or abandon the failing connection without claiming an outcome.
2. Open a fresh read-only connection with the same pragmas.
3. Authoritatively read whether the expected state/version changes and matching journal row are present.
4. If both are present → report the encoded true outcome (`completed`, `rejected`, or `error`).
5. If neither is present → report operation error `persistence.failed` without claiming mutation.
6. If only one is present → treat as integrity failure and report `persistence.failed`; state and journal **MUST** remain atomic in normal operation.

## Rollback narratives

| Failure point | SQLite effect | Caller-visible outcome |
|---|---|---|
| Migration SQL error mid-file | Migration transaction rolled back; version not advanced | Open fails; no dispatch |
| Registration mutation constraint violation | Full write transaction rolled back | Mapped domain rejection per [SQLite constraint mapping](#sqlite-constraint-mapping); catalog unchanged |
| `provider.disable` token mismatch or traversal binding failure | Rolled back | `catalog.ack_token.stale` or `catalog.ack_token.invalid` rejection |
| `run.create` recheck failure | Rolled back | `provider.registration.stale`; no run/journal |
| Gated transition CAS failure | Stale journal inserted or rolled back as a unit | `state.stale_version` error; state unchanged |
| Transition rejected (gate/domain) | Journal appended; state unchanged | `rejected` outcome |
| `run.label` terminal lifecycle re-read | Journal appended; label unchanged | `rejected` `run.lifecycle.terminal` |
| `SQLITE_BUSY` after `sqlite_busy_timeout_ms` | No commit | Persistence error; no claimed mutation |
| Commit I/O error after provider success | Outcome unknown on failing connection; verify on fresh connection per [Commit outcome verification](#commit-outcome-verification) | Report true outcome when mutation is provably present; otherwise `persistence.failed`; **MUST NOT** claim rollback or unchanged state without authoritative read |
| Process crash before `COMMIT` | SQLite WAL recovery | No partial application mutation; journal/state remain consistent |
| Process crash during provider | No write transaction open | No durable effect from that invocation; prior state intact |

Persistence failure **MUST NOT** report evidence or state as committed without proof ([testing.md](testing.md)).

## Read snapshot for export

`run.export` reads one consistent snapshot of authoritative state and journal rows without mutating. Export files are not registered in SQLite and are not replayed into the database.

## Test-only fault injection

Atomicity E2Es may inject SQLite abort triggers or fixture corruption **only** through test harness setup (for example `LOOP_ENGINE_HOME` temp database paths, pragma hooks, or pre-seeded broken pages). Production integration code **MUST NOT** contain fault-injection branches keyed on environment or compile-time test flags.

## Deliberate exclusions

- ORM query builders that obscure transaction scope.
- Event-sourced projection tables rebuilding current state from journal.
- Second on-disk authority (JSON journal write path, shadow config DB).
- Long-running `BEGIN` during provider subprocess.
- Individual-run deletion or silent compaction (I45).
- Active-run graph migration or gate bypass persistence.

## Verification rules (T009)

- `synchronous=FULL` with acknowledged-commit durability narrative matches [Connection pragmas](#connection-pragmas) and [Acknowledged-commit durability](#acknowledged-commit-durability).
- `busy_timeout` references `sqlite_busy_timeout_ms` only; no independent numeric literal.
- Gate-free `run.request` state changes linearize re-read, resolve, and mutate inside one write transaction with version CAS.
- `run.evidence.add` always appends a journal entry in the same transaction as evidence insert.
- Post-lookup `run.guidance` and `run.compatibility` rejections/errors, including terminal denial, append attempt journal when persistence is available.
- `run.label` re-reads `lifecycle` inside its write transaction; terminal re-read preserves label and appends `label.changed` rejection atomically; label mutations do not bump workflow/lifecycle versions.
- Both writer orders for `run.label` vs `run.request` final transition and `run.label` vs `run.terminate` are explicit.
- Commit I/O failure uses fresh-connection verification; outcomes never falsely claim rollback or mutation.
- Disable acknowledgement tokens and cursor v1 MACs use the installation `integrity_key` with documented domain separation; key is never exposed through CLI/trace/export.
- Expected `SQLITE_CONSTRAINT` failures map to frozen domain reason codes; unexpected integrity failures map to `persistence.failed`.
