## Architectural rule

Dependencies point inward. Core defines workflow graph semantics, run state, transition decisions, operations, and contracts for capabilities it needs. Integrations invoke providers, persist state/journal, and access external technology. CLI translates user interaction and wires concrete implementations.

Layer count is not a goal. Three product crates exist because they create useful compiler-enforced boundaries.

## System boundary

```text
workflow provider executable
  ├─ emits normalized graph
  ├─ evaluates named gates
  ├─ gate evaluation may produce bounded evidence
└─ live guidance produces advisory text only
                 │
                 ▼
        loop-engine integrations
                 │
                 ▼
       core operations and model
                 │
                 ▼
 authoritative state + immutable journal
```

Provider is sole workflow-authoring source. Normalized graph is an engine-facing projection generated by provider, not an independently maintained workflow definition.

## Product crates

### `loop-engine-core`

Core contains no CLI, SQLite, configuration parser, process runner, or provider-protocol transport.

Internal sections:

- `model`: validated workflow graphs, optional immutable run inputs, run state, state/event/gate identifiers, transitions, gate verdicts, append-only evidence, provider identity, journal facts, and deterministic transition decisions.
- `capabilities`: contracts consumed by operations, including atomic run persistence, provider invocation, time, and identifier generation.
- `operations`: provider registration list/add/update/rename/disable/restore/validation/conformance, compatibility check, run creation/list/show/graph-inspect, evidence append/list, event request, annotate, label, terminate, history, audit export, and explicitly requested live-guidance orchestration.

Internal dependency direction:

```text
operations → capabilities → model
operations ───────────────→ model
```

Model must not import operations or capabilities. Capability contracts use core model types rather than integration records.

Core does not replay journal entries to derive current state. `model::run::Run` stores current state and lifecycle directly; `model::journal::JournalEntry` is an immutable explanatory fact. Capability traits accept immutable resolved provider configuration, bounded snapshots, or operation-specific atomic commands; no generic save/update repository exists. Event attempts compare workflow/lifecycle versions and commit state, evidence, associations, and journal facts through one command. Provider invocation has five typed roles, no catalog lookup, and an explicit pre-launch trace-budget-unavailable result. Run reads and exports require no provider.

All 21 frozen operations are exposed through production CLI routes; `operations::catalog::exposed_operations()` is the authoritative exposed inventory. Provider calls accept one immutable resolved configuration and typed, encoded-size-bounded run/evidence snapshots. Run creation commands carry the catalog revision to recheck. Event commands carry both the resolved journal draft and the stale-version error draft so persistence can select one atomically. Journal drafts exclude transaction-owned sequence, authoritative before/after state facts, and exact encoded-size accounting; persistence supplies those only after its write-lock recheck. Journal-bearing mutation commands validate run/operation/kind authority before crossing the persistence boundary. Operations call narrow catalog, reader, writer, event-writer, and exporter capabilities rather than exposing repositories. Public operation closure requires matching core, driver, route, E2E, trace, facet, and documentation evidence.

### `loop-engine-integrations`

Integrations translate external systems and representations to core capabilities and types.

Expected integrations:

- executable-provider subprocess protocol ([provider-protocol-v1.md](provider-protocol-v1.md));
- selected SQLite transactional persistence integration;
- machine-local provider registration and global/project CLI-default loading;
- system clock;
- identifier generation;
- provider graph/result JSON mapping;
- journal/state JSON and JSONL export;
- per-invocation rotating structured diagnostic sink.

Integration-specific errors and records are translated before crossing inward.

### `loop-engine-cli`

CLI is production delivery mechanism and sole composition root.

It owns:

- argument parsing;
- machine-catalog and CLI-default location resolution per [configuration.md](configuration.md);
- stable provider-registration resolution;
- human-readable rendering;
- structured JSON response rendering;
- exit-code mapping;
- construction of concrete integrations;
- secure operational-trace initialization before dispatch;
- invocation of one core operation per user intent.

CLI must not select transitions, reinterpret provider verdicts, or make workflow-policy decisions.

## Application operation catalog

MVP exposes exactly **21** stable application operation IDs defined by [operation-catalog.md](operation-catalog.md). Two namespaces:

**Provider (7):** `provider.add`, `provider.list`, `provider.check`, `provider.update`, `provider.rename`, `provider.disable`, `provider.restore`

**Run (14):** `run.create`, `run.list`, `run.show`, `run.graph`, `run.history`, `run.evidence.add`, `run.evidence.list`, `run.annotate`, `run.label`, `run.request`, `run.guidance`, `run.compatibility`, `run.terminate`, `run.export`

Provider-catalog mutations are authoritative catalog changes, not run-state mutations; verification uses fresh `provider.list` with no per-run journal (I40). Registration-wide active-graph conformance is owned by `provider.check --active-runs`; per-run explicit compatibility with journal facts is owned by `run.compatibility`. CLI help, `--list-operations`, version display, and internal provider protocol roles are not application operations.

## Provider model

Workflow authoring is code-only. Any executable language may implement the provider protocol defined in [provider-protocol-v1.md](provider-protocol-v1.md).

Immutable machine-local registration ID is logical workflow identity. Enabled registration also has mutable human handle unique among enabled registrations and explicitly names executable, arguments, and working directory. Active run stores ID, so caller CWD, handle rename, and project defaults cannot rebind it. Same executable may back several registrations. Registration `executable` and `working_directory` are stored as lexical-normalized absolute paths at mutation time ([configuration.md](configuration.md)); provider invocation uses those stored absolutes, never caller CWD. Engine computes graph-revision identity from canonical validated projection; provider path/observed executable digest and self-reported version remain best-effort invocation audit facts, not complete semantic identity.

Provider protocol v1 transport (fresh process, stdin/stdout JSON envelopes, `protocol_major` 1) is frozen in [provider-protocol-v1.md](provider-protocol-v1.md). Five narrow roles:

- describe complete input-independent graph, optional run-input declarations, static guidance, and live-guidance capability without candidate values;
- validate candidate creation inputs without returning topology;
- evaluate required named gates against bounded engine-supplied run snapshot and return verdicts/evidence, explicit incompatibility, or evaluation error;
- generate explicitly requested live advisory guidance;
- check compatibility with active stored graph.

Provider must remain able to evaluate gate identifiers used by active stored graphs or return explicit incompatibility.

Provider cannot:

- write current engine state directly;
- append authoritative journal entries directly;
- introduce undeclared transition during gate evaluation;
- make actor identity a hidden source of authority.

Configuring provider's explicit executable locator authorizes its execution with caller permissions. Engine process isolation is not a security sandbox. MVP has no separate trust database, provider scanning, package registry, or installer.

## Run creation and graph snapshots

Run creation follows this direction:

1. Caller identifies machine-local provider registration.
2. Integration invokes input-free graph-description operation; provider returns complete graph, input declarations, static presentation, and live-guidance capability.
3. Integration maps protocol DTO; core validates states, final sinks, one transition per `(state,event)`, identifiers, and supported semantics.
4. When input declarations or candidate values exist, caller-supplied values go to separate validation operation returning acceptance/diagnostics only. Both calls use same resolved registration configuration and observed executable digest when available; detected change errors creation. Digest does not cover interpreted dependencies or environment. Engine enforces protocol shape/bounds.
5. Persistence atomically stores run ID, optional label, inspectable accepted immutable inputs, initial authoritative state/lifecycle, canonical full-projection digest/snapshot, stable provider-registration ID, and creation journal entry.

Provider-emitted invalid graph is operation error and creates no run/journal. Invalid caller input is domain rejection and creates no run/journal.

Safe inspection later reads stored graph without provider execution. Explicit compatibility checks and provider-dependent operations execute current provider and fail clearly when it is incompatible.

## State-changing operation flow

Before dispatch, CLI creates current-user-only per-invocation JSONL trace. Trace initialization failure stops invocation before operation/provider/persistence work.

1. CLI parses request and creates plain core operation input.
2. Operation loads authoritative current run state, lifecycle, workflow-state/lifecycle version, inputs, caller-selected evidence, and stored graph.
3. Core resolves requested event to exactly one transition.
4. If transition has gates, operation asks current registration executable to evaluate all required gates in one invocation against bounded loaded snapshot. Gate-free transition skips provider.
5. Integration accepts exactly one semantic result: complete pass/fail verdict set, explicit incompatibility, or evaluation error. It validates bounded provider evidence only on verdict result, records actual locator/digest, and maps result.
6. Core deterministically completes, rejects, or errors from stored graph, prior state, request, and observed result.
7. After provider returns, persistence commits only if workflow state/lifecycle version still matches evaluated snapshot, then atomically updates authoritative records plus journal. No persistence write lock is held across provider invocation. Stale evaluation errors without transition; concurrent label/note/evidence append does not invalidate.
8. CLI renders outcome without adding policy.

External provider behavior may vary. Core decision given observed verdicts does not.

Stored run state is direct read authority; journal never reconstructs it. Core row reconstitution accepts validated stored graph, current state/lifecycle, and checked positive internal versions from persistence mapping; it is not event replay. Transition decisions bind run ID, source state, stored selector/target/gates, and evaluated versions before mutation. Completed self-loops apply the stored transition without changing workflow-state version. SQLite operations still own atomic CAS and durable commit.

## Run interaction and lifecycle

Run lifecycle has three concepts:

- active: events may be requested;
- final: stored graph entered any declared final sink state; domain meaning comes from state ID/provider metadata;
- terminated: caller explicitly closed run.

Graph may have zero, one, or several final states. Zero-final run is intentionally ongoing and can close only by termination. Initial final state creates immediately final run. Final states have no outgoing transitions; non-final sink is valid terminate-only trap. Every actionable state stores static guidance or explicit no-guidance declaration.

Final and terminated runs never reopen or accept events, report no requestable events, remain safely inspectable, and may receive append-only notes/evidence. Termination may include note. No pause/resume status exists because process exit already stops activity. MVP does not delete individual runs.

Machine-local catalog supports one local user operating several independent runs, resolves stable run IDs from any caller working directory, and lists active runs by default. Provider-free current-work inspection may show current slice; dedicated graph inspection exposes full stored projection. Run may have optional non-unique display label, mutable and journaled only while active.

Evidence and notes may be appended independently or included with event request. Inline evidence stays attached to every durably recorded attempt. Public UX assumes one current caller per run; CLI does not expose optimistic revision tokens, claims, leases, idempotency keys, or automatic retries.

Public operation outcomes have three semantic classes:

- completed: requested operation achieved its purpose;
- rejected: request was understood but domain validation denied it;
- errored: request could not be reliably evaluated or committed.

Stored-graph/lifecycle/failed-gate/caller-input/evidence-selection/unsupported-guidance and explicit capability incompatibility denials are rejections. Invalid provider graph, tombstoned/missing registration/executable, unsupported protocol major, creation drift, provider execution/protocol/evaluation/evidence failure, stale workflow-state/lifecycle version, and persistence failure are errors. Explicit compatibility report completes even when findings include incompatibility. Missing/tombstoned provider affects only provider-dependent requests; gate-free events and all provider-free operations continue. Detailed reason codes preserve recovery path. Normal run output reports current state, whether state ID changed, and next requestable events when available; completed self-loop reports unchanged state.

## Operational diagnostics

Instrumentation uses three stable choke points:

- CLI operation dispatcher records request ID, operation identity, bounded request payload, and completed/rejected/error outcome;
- executable-provider integration records locator/digest/version, configured arguments, bounded protocol request/result, captured stdout/stderr, timing, and execution outcome;
- persistence integration records transaction intent, applicable workflow-state/lifecycle version check, and commit/rollback outcome.

Core emits targeted structured events for consequential transition, gate, lifecycle, compatibility, and stale-state decisions not explained by boundary payloads. Pure helpers need no logging requirement. Production code must not gain alternate provider, persistence, or operation-dispatch paths that bypass these choke points.

One structured JSONL file belongs to one CLI invocation, is correlated by request ID, and rotates within configurable file-count/total-byte bounds. Trace retains all bounded engine/provider payloads without redaction; inherited environment is excluded. Trace files require current-user-only access. Operational diagnostics are not authoritative workflow state, evidence, or journal and may be removed by rotation. Rich errors expose failure phase and trace location when available; trace-initialization failure remains visible on stderr.

This architecture intentionally avoids trace context threaded through every function, mandatory per-function attributes, custom compiler lints, and source-level log counting. Compiler visibility and crate boundaries protect choke points; black-box trace contracts prove observable behavior.

## Provider and graph drift

Provider implementation and gate policy are live and may change between invocations. Active run resolves current executable/arguments/working directory from stored machine-local registration ID. Each durably observed gate result records actual locator and digest/version so drift is visible. Drift needs no approval, but provider must report incompatibility when current policy no longer honors stored declarations/guidance.

Stored graph remains fixed for active run. Engine does not ask latest provider to redefine active topology. Provider gate code must handle gate IDs from stored graph; incompatibility fails closed and is journaled.

Provider graph changes affect new runs only. MVP has no active-run graph migration or gate bypass. Compatibility reports are non-latching and capability-scoped: unsupported event/guidance rejects while supported and gate-free events remain usable. Run remains inspectable, annotatable, and terminable. Registration executable configuration may be disabled after warning about affected active runs; tombstoned ID is restorable with any currently free handle. Reused handle never rebinds runs because they store ID.

## Persistence authority

Normative SQLite pragmas, migration policy, transaction boundaries, workflow/registration CAS, catalog-mutation digest guards, and rollback narratives: [persistence.md](persistence.md).

Current run state and lifecycle are authoritative records. Internal workflow-state/lifecycle version guards evaluated transitions and is not caller-managed token; annotation/label versions do not invalidate gate evaluation. Journal is append-only explanatory history.

Every run mutation and required journal fact commit in one transaction. No write transaction spans provider subprocess execution ([persistence.md](persistence.md) § No write lock across provider). Provider capability results and attempted-transport errors carry exact bounded `ProviderFact` values so operation command validation can bind journal observations to the actual invocation; pre-launch trace-budget failure carries none. Event persistence returns whether expected-version or stale-version journal branch committed, and caller outcome follows that authoritative branch. Label persistence materializes `label_before` from its in-transaction authoritative row instead of freezing a pretransaction value in the command.

Completed transition transaction contains at minimum:

- evaluated workflow-state/lifecycle version and prior state;
- state/lifecycle update;
- provider/gate observations when gates exist;
- completed transition outcome;
- new workflow-state/lifecycle version.

After successful run lookup, every syntactically valid event request appends all-or-nothing explanatory attempt record with inline/provider evidence and selected-evidence associations when persistence remains available, even when event is unknown, lifecycle denies it, or workflow state does not change. Abrupt process death may leave no record of provider process that engine never observed.

No event fold, replay reducer, or historical provider execution is required. Journal may expose state-before/state-after facts without promising full historical reconstruction.

## Boundary data

External representations use dedicated DTOs:

- provider graph/result JSON DTO to core graph/verdict/evidence;
- engine config DTO to resolved settings;
- selected SQLite persistence-record DTO to core state and journal facts;
- CLI argument DTO to operation request;
- operation outcome to human or structured CLI response DTO.

Core types do not derive serialization merely because an external representation needs it.

## Narrow interpreter boundary

Accepted MVP direction:

- provider-emitted runtime graph;
- flat graph;
- exactly one active workflow state;
- one explicit initial state and optional final sink states;
- externally submitted named events;
- at most one transition per `(state,event)` and deterministic selection;
- named provider gates;
- cycles and self-loops;
- atomic authoritative-state/journal persistence.

Outside MVP:

- hierarchical states;
- parallel regions and fork/join;
- timers and schedulers;
- automatic primary work;
- child workflows;
- compensation;
- distributed queues/workers;
- mutable workflow variable bag;
- embedded expression language;
- provider-directed state mutation.

If requirements gain several excluded features, reassess mature workflow runtimes rather than incrementally becoming general platform.

## Provider-authoring support

Engine publishes protocol schemas and examples, returns actionable diagnostics, and exposes conformance checks for provider protocol, emitted graph, and active-run compatibility. Official language SDK is not required for MVP.

Provider connection is explicit machine-local registration command/configuration. Authors distribute executable plus documented registration command. Engine does not scan project files, discover executable packages automatically, import registration manifests, or resolve provider registry names.

Conformance covers protocol framing/handshake, operation result shapes, input-free description/value-only validation separation, graph validity, and active-run compatibility. Provider authors remain responsible for semantic tests of gate and guidance logic.

## Composition and enforcement

Concrete construction occurs only in CLI composition root. Core does not instantiate process or persistence integrations.

Cargo manifests document crate-level direction. Core's internal model/capabilities/operations separation and approved integration/composition boundaries are architectural constraints; product code must not introduce direct provider, persistence, or dispatch bypasses.


Do not create generic repositories, catch-all services, `util`, `common`, or interfaces beside implementations. Add capability only for external side effect or genuine contract boundary.

## Testing posture

Architecture is exercised through production CLI E2Es using real executable provider fixtures and real persistence. Lower-level tests do not establish behavioral completeness. See [testing.md](testing.md) and normative [interaction storyboards](ux-storyboards.md).

The [reference software-change workflow](reference-workflow.md) is both motivating example and required end-to-end acceptance case. Its software-specific concepts must remain outside core.
