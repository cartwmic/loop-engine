What changed

A driver can now build steps in parallel worktrees and land them by merge

In implement, the lean-change skill now tells the driver to build steps that touch different files at the same time, each in a git worktree outside the repository, land each into the repository with git merge --no-ff in plan order, run the full build and suite once on the joined tree, then remove the worktrees and step branches crates/lean-change-provider/skills/using-lean-change-provider/SKILL.md:118-167. The engine and the provider are untouched: the recipe is prose plus three shell blocks the driver runs.

The journey extracts those three blocks from the skill and runs them against a fixture repository with two scripted builders, a conflicting step and a hook-rejected step scripts/lean-change-journey.py:409-534. The PRD records the recipe as live requirement LE-211 docs/PRD.md:2266-2273. The PR description cites a driver-model evaluation kept outside the repository; nothing in the diff carries it.

Checkpoint A

Should cleanup delete a step that committed but never landed?

The land block commits in the step's worktree before it merges, so a step that stops at conflict leaves a commit on step/$STEP that is not in the repository crates/lean-change-provider/skills/using-lean-change-provider/SKILL.md:143-144. Cleanup removes the worktree, which is clean, then runs branch -D; the warning beneath it speaks only of uncommitted work. The journey cleans its conflicting step s3 this way and asserts that no step/* branch is left. The reviewer decides whether losing that commit is the intended end of a conflict.

Checkpoint B

Does the land block's “conflict” mean a conflict whenever the merge fails?

When git merge fails for any reason, the fallback runs merge --abort and prints conflict: $STEP, and the prose then sends the driver to resolve a conflict crates/lean-change-provider/skills/using-lean-change-provider/SKILL.md:150-153. The recipe also has the driver fix gate findings in REPO crates/lean-change-provider/skills/using-lean-change-provider/SKILL.md:155-156. A merge refused before it starts, over an uncommitted edit in REPO, leaves nothing to abort and still prints conflict uncertain; running the land block against a repository with an uncommitted edit to a file the step changes would settle it. The journey's one conflict is a real conflict on a clean repository.

  • Land block One label for every way the merge can fail.
    ▸ crates/lean-change-provider/skills/using-lean-change-provider/SKILL.md:143-147 At head 
       if git -C "$WORK/wt-$STEP" add -A && git -C "$WORK/wt-$STEP" commit -q -m "step $STEP"; then
     git -C "$REPO" merge -q --no-ff --no-edit "step/$STEP" || { git -C "$REPO" merge --abort; echo "conflict: $STEP" >&2; false; }
   else
     echo "not committed: $STEP" >&2; false
   fi
  • The conflict case the journey pins s3 edits a line s1 landed, on a clean repository; HEAD, status and tree identity hold. scripts/lean-change-journey.py:464-469

Checkpoint C

Is the parallel scenario the proof LE-211 needs, at the cost it adds to every full journey run?

LE-211 is live with coverage e2e/journey, and its bookends:LE-211 marker sits on the scenario scripts/lean-change-journey.py:411. The scenario runs the skill's blocks as written, with scripted builders that wait up to 20 seconds for each other. It shows the blocks do what the prose says; it does not show a model driver following the recipe, which the requirement's known limits leave to a small fixture docs/PRD.md:2273. Every full run now parses the skill first and exits unless the section holds exactly three sh blocks, so a wording edit to the skill can stop the b, c, hard and old-vs-new profiles too.

  • Builder start barrier A builder fails if the other has not started within 20 seconds.
    ▸ scripts/lean-change-journey.py:370-378 At head 
    def builder(worktree, step, other, name, text, starts):
    """A scripted builder: records its start, waits until the other builder has started, then writes only its own file."""
    (starts / step).touch()
    deadline = time.monotonic() + BUILDER_TIMEOUT
    while not (starts / other).exists():
        if time.monotonic() > deadline:
            raise TimeoutError(f'builder {step}: {other} never started; the builders did not run at the same time')
        time.sleep(0.05)
    (worktree / name).write_text(text)
