This file governs the entire loop-engine checkout: `loop-cli` (`loop-engine`), `loop-core`, `loop-integrations`, `bookends-check`, the lean-change/policy-document/research providers, `tests/workspace-integration`, `tests/fixtures`, `tests/bounded_process.rs`, scripts, skills and release workflows. `crates/bookends-check` has no nested guide and follows this file.

Primary workflow work belongs outside the engine/provider. Do not invent engine policy, review orchestration or core semantics. Humans start at [README.md](README.md). Nested `AGENTS.md` files add crate-local procedure and must not contradict this file.

For software design, build and review, follow the owner's design principles in `~/.local/share/agent-harness/design-principles.md`. It is a prose path, not a markdown link, because a link would escape the checkout (see Document and Git safety).

## External work

Before driving the CLI, load [the engine skill](skills/using-loop-engine/SKILL.md) and [agent usage](docs/agent-usage.md). Before commissioning provider work, load its crate-local guide to select supported commands and its skill. Each run has one logical mutating driver: serialize all mutations through that driver, rather than starting independent concurrent mutators.

**Terms.** The *driver* is the one agent that owns a run, or a change without a run, and acts for it. For a run it is the logical mutating driver above (the engine's term, as [docs/agent-usage.md](docs/agent-usage.md#external-driver-loop) uses it). Who may do which Git step is set by the Workflow table and the Git checkpoint bullet in Document and Git safety, not by this definition. A *worker* is an agent that the driver or a lead commissions to do part of the work; an agent commissioned to drive a whole run is that run's driver. A *lead* is the agent that briefed the work, and may also be the driver. "Run driver" is not a second role: say "driver". "Driver-owned" means owned by the driver (catalogs, proof directories, scratch folders), and script names such as `external_work_driver.py` keep their names.

Test catalogs and captures belong in driver-owned directories outside the checkout: explicitly set database and provider config, and unset unintended LOOP/XDG redirects rather than using user state.

Before rebuilding or replacing a provider executable, inspect active runs in each driver-owned catalog with explicit database/config and full show. Runs freeze command/args paths, not executable bytes. If an active run points to a build output that would be overwritten, stop the build: retain that executable and its required runtime dependencies at the exact frozen path, and build new binaries into a separate `CARGO_TARGET_DIR`. Do not move the old binary and assume the run follows it; there is no migration. Resume only with the compatible runtime preserved or after an authorized termination of the affected run.

## Workflow

Run from the repository root with Rust/Cargo and Python 3 (CI uses 3.14.6). Load the engine and active provider skills; use policy-document for README/AGENTS authoring or assessment. Proof runs in stages, each with one owner:

| When | Who | What runs |
|---|---|---|
| Before handoff | Worker (never stages, commits, pushes or opens the PR unless the recorded Git checkpoint decision names the worker for that step; see Document and Git safety) | The `checks` job's commands, on kgate (see Where proof runs below): `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo build --workspace --locked`. Then the [Boundary checks](#boundary-checks) rows for the areas the change touches, and `cargo test -p <crate>` for each touched crate. `cargo test -p` runs unit tests only: every crate with a `tests/` directory sets `autotests = false`, and its `tests/*.rs` files run through `tests/workspace-integration`. So for a touched crate with `tests/*.rs`, also run `python3 scripts/run-central-tests.py --filter <module>` (module names are in `tests/workspace-integration/tests/workspace.rs`, for example `loop_cli_engine`, `research_cli`). The handoff reports those commands and their outcomes. Missing required boundary proof blocks completion. |
| On the PR | Driver, who pushes and opens the PR once the Git checkpoint below allows it, unless that decision names the worker | The `checks` job of [ci.yml](.github/workflows/ci.yml), on the PR head; a PR runs nothing else. It ends with the Bookends gate over the commits the PR adds on top of main (merge base to PR head). The driver cites its run URL and head SHA. |
| Merge | Driver | When the PR `checks` run is green on the current head and a fresh reviewer PASS on that same head exists, the driver squash-merges through the gate, never with a bare `gh pr merge` (the Bash hook refuses it): `ci-main-status --merge-gate loop-engine && pr-body-check loop-engine <pr> && gh pr merge <pr> --squash --match-head-commit <head sha>`. `--merge-gate` stops only a red main (an untested tip may merge), and `pr-body-check` reads the PR body against playbook rules ecd63156 (principles table), 385acc43 and ccc6c94b (the `Decisions:` line); its error message names what is missing. `gh pr create` and `gh pr edit` are refused until `pr-body-check --body-file <file>` passes on the body. The authority is standing grant 46 (see Document and Git safety), which has exactly that condition; it is the owner's standing rule for his personal computer, from his global agent instructions: "Merging and deploying approved work is yours to do: if checks pass and it keeps the product requirements, ship it and tell me after." The driver reports the merge to the owner after. |
| After merge | Driver | The push run of [ci.yml](.github/workflows/ci.yml) on main for the merge SHA runs `checks`, `tests` (workspace tests, journey self-tests, Bookends over the pushed range) and `release-tests`, one run per push, never cancelled. See [After merge](#after-merge-the-main-push-run). |

**Join-step proof.** When a lean-change run builds steps with the [Parallel builders](crates/lean-change-provider/skills/using-lean-change-provider/SKILL.md#parallel-builders) recipe, builders run only focused tests. After the last independent step lands, and before `ready`, the driver runs the join proof once on the joined tree in the repository: the Before handoff row's commands (the fmt, Clippy and build job below, and `cargo test -p <crate>` for each touched crate, with `scripts/run-central-tests.py --filter <module>` where that row asks), then the Boundary checks rows for the areas the steps touched. For the lean-change provider that means `J:lean-change`, `J:lean-change-mutations` and `J:external-work`, run through the kgate journey command below. It runs on kgate (playbook rule 83fbe006); the host runs it only under one of the three exceptions below. A fix or the wire-up step after it changes the tree, and a kgate run covers only the tree it shipped, so run again on the final tree. Record it as every kgate job is recorded in Completion and handoff: the run-and-wake job id, the `tree` hash from the kgate record, the log path and the exit code of each command. Missing or partial proof blocks `ready`.

**Where proof runs.** fmt, Clippy, build, `cargo test -p`, `scripts/run-central-tests.py`, and the Boundary checks journeys run on kgate, not on the host (playbook rule 83fbe006). Run from the repository root; kgate ships that tree's tracked and untracked-not-ignored files, so an edit after a run needs a fresh run. Start the job with `run-and-wake`. If a wake can reach you, end your turn and wait for it; a subagent or a session with no wake target cannot be woken, so it must not end its turn but poll the job's `end` record in `${XDG_STATE_HOME:-~/.local/state}/run-and-wake/log.jsonl`. Read the result as [Read the result](docs/kgate-baseline.md#read-the-result) says; it applies to every kgate job here, not only the baseline.

```sh
run-and-wake -- kgate --profile kgate-verify.toml -- sh -c 'set -e; cargo fmt --all -- --check; cargo clippy --workspace --all-targets --locked -- -D warnings; cargo build --workspace --all-targets --locked'
run-and-wake -- kgate --profile kgate-verify.toml -- cargo test -p <crate> --locked
```

[kgate.toml](kgate.toml) is the 12-CPU baseline profile; [kgate-verify.toml](kgate-verify.toml) (4 CPUs, same image and tools) fits everything smaller. A journey needs the binaries it runs, so build and run it in the same job. The command below downloads cargo-dist 0.32.0 (the version `mise.toml` pins; the pod has no mise and no `dist`, and rows such as `research-journey.py --mode source`, `generate-release.py --check` and `assert-release-gates.py` need it) and puts it first on `PATH`, builds, resolves `BIN_DIR` in the pod, sets `PROOF_ROOT=/out/proof`, then runs the row commands from the Boundary checks table. Pass them, written out from the `J:` definitions under Boundary checks below, as the one single-quoted argument after `journey`, joined with `&&` (the definitions use double quotes only, so they need no escaping):

```sh
run-and-wake -- kgate --profile kgate-verify.toml -- sh -c 'set -eu; export HOME=/tmp/h PROOF_ROOT=/out/proof; mkdir -p "$HOME" /tmp/dist; python3 -c "import urllib.request, tarfile, io; u = \"https://github.com/axodotdev/cargo-dist/releases/download/v0.32.0/cargo-dist-x86_64-unknown-linux-gnu.tar.xz\"; tarfile.open(fileobj=io.BytesIO(urllib.request.urlopen(u).read())).extractall(\"/tmp/dist\")"; export PATH="$(dirname "$(find /tmp/dist -name dist -type f | head -1)"):$PATH"; cargo build --workspace --all-targets --locked; BIN_DIR="$(cargo metadata --format-version 1 --no-deps | python3 -c "import json,sys; print(json.load(sys.stdin)[\"target_directory\"] + \"/debug\")")"; export BIN_DIR; sh -c "$1"' journey '<row commands, joined with &&>'
```

A job whose kgate record has a non-empty `reason`, or has no kgate record, did not run to its end: that is missing proof, neither a pass nor a failure. A pod's `/tmp` is lost when the job ends, so write anything the handoff must cite to `/out`; it comes back to `~/.local/state/kgate/<id>.out/`.

The host runs one of these jobs only under one of the rule's three exceptions: (1) kgate cannot run the job (it needs the host's own state, apps or hardware), (2) kgate has no capacity for it, or (3) the owner explicitly asks for a local run instead of the cluster. The handoff names which of the three applies, in one line.

The full baseline on kgate (profile [kgate.toml](kgate.toml)) is not run before merge by default: the push run carries it. The driver or lead may decide, before the PR opens, to run it for changes to public tests, `bookends.toml` pathspecs, `scripts/bookends-check-gate.sh` or release scripts, or anything they judge risky; it includes the workspace tests and Bookends. A worker runs it only when told to. Run it when the owner asks. A culprit hunt on a red main does not run it (see After merge). Load [docs/kgate-baseline.md](docs/kgate-baseline.md) first: it holds the run command, how to read the result and the tree-hash check, and a baseline counts as proof only per that file.

Keep the check list in `scripts/baseline.sh` identical to the union of the jobs in [ci.yml](.github/workflows/ci.yml): fmt, locked all-target Clippy, locked workspace build, workspace tests, five bare journey self-tests, the lean-change mutation applicability check, the release-after-merge script tests in 8 parallel shards (`python3 scripts/run-release-tests-sharded.py`; it runs the tests of `scripts/test_release_after_merge.py`, keeps one log per shard and fails if any shard fails or any test is missing), the PRD prose check tests (`python3 scripts/test_prd_prose_check.py`), the triage skill copies tests (`python3 scripts/test_triage_skills.py`), Bookends with bypass unset. Bare journeys and `--self-test` prove collection/interface mechanics, not end-to-end progression. Full journeys in [journeys.yml](.github/workflows/journeys.yml) are informational and never gate Release; local boundary proof remains required.

### After merge: the main push run

Check the push run for the merge SHA before merging anything else. Poll `gh run list --workflow ci.yml --branch main --event push --commit <merge sha> --json databaseId,status,conclusion` (every 30 seconds, as `release-after-merge.sh` does) until a run appears, then wait for it to finish: `gh run watch <run id> --interval 60 --exit-status`. Push runs are never cancelled, so a missing run is not restarted. If no run appears within 10 minutes, report it to the lead and merge nothing further. If the run is red:

1. Merge nothing else into main except the fix, and cut no release.
2. Rerun the failed jobs once: `gh run rerun --failed <run id>`. If it goes green, it was a flake: file an issue naming the test, and the freeze ends.
3. If a push run of [ci.yml](.github/workflows/ci.yml) on main is still red after one `gh run rerun --failed <run id>`, find the culprit commit with [docs/culprit-hunt.md](docs/culprit-hunt.md) before reverting anything.
4. Revert the culprit with a normal PR: `git revert <sha>` for a squash commit, `git revert -m 1 <sha>` for a merge commit. It needs only `checks` plus a one-line review, and main's next push run must go green. The culprit's owner then fixes forward in a new PR.
5. A fix-forward PR runs `checks` only on a pull request, so the red-main merge gate has no full-suite run of its head to accept. Run one by hand: `gh workflow run ci.yml -R cartwmic/loop-engine --ref <branch>`. A manual run executes `checks`, `tests` (with Bookends over the commits the branch adds on top of main) and `release-tests` on the branch head, and `ci-main-status --merge-gate loop-engine --pr <n>` accepts it. A manual run on main (`--ref main`) re-checks main's tip commit from its first parent; it checks that one commit only.

These steps are the driver's job under coordinator playbook rule fab9b713, which every brief for build or merge work carries (its sources include the owner's pick of batching on ask #847): find the culprit in the red range and revert it with a normal PR. They need no further ask: the flake rerun, the culprit hunt of [docs/culprit-hunt.md](docs/culprit-hunt.md) with its kgate runs, and the revert PR's commit and push. That method creates a detached worktree (two places in it do) and removes it when the hunt ends. Removing these worktrees is part of the method fab9b713 calls for; no ask or grant names them, so it is not an explicit grant. Any other worktree removal is deleting (see Document and Git safety).

## Document and Git safety

- Draft or revise README.md/AGENTS.md through policy-document using a copied `readme-4`/`agents-4` profile with `mode: "draft"`. Use `mode: "audit"` for assessment. Load the policy-document skill for profile preparation and evidence rules. Local references must remain within the target directory; normalized paths such as `docs/../exists.md` are allowed, but escapes outside the directory are rejected. For root guidance in crate documents, use an explicit checkout-root-relative prose path instead of an escaping markdown link.
- The coordinator or the lead that briefed the work records the Git checkpoint decision before the first Git step it covers: after implementation triage and before pre-review proof, or, when the plan uses the lean-change Parallel builders recipe, before the implement step (the brief may carry it). The owner is not asked for it: committing, pushing a branch and opening a PR without merging are the coordinator's or briefing lead's decisions (coordinator playbook rule 90fe4b7b; for the briefing lead, the owner's global agent instructions, which have agents decide what does not materially matter, and ledger decision #2984). A repository checkpoint does not create a commit. The decision names who stages and commits, who pushes, and who opens the PR (each the driver or the worker); until it is recorded nobody does any of these, and once it is recorded only the party it names does each. The same decision covers creating a worktree or branch, which deletes nothing, and the lean-change skill's step worktrees, step commits and landing merges ([Parallel builders](crates/lean-change-provider/skills/using-lean-change-provider/SKILL.md#parallel-builders)): those steps need a decision that names the driver as committer, the driver does them, and no builder commits. Authorized Git identity changes require fresh applicable proof; do not relabel receipts.
- Merging to main needs no ask once a fresh reviewer PASS (the reviewer seat in the coordinator's seat table) on the head and green CI exist (standing grant 46, Michael's standing grant for this repository, which replaced grant 22 on 2026-11-16; list grants with `ledger list grants` in the coordinator ledger). The grant's own exclusions read "Loop Engine run starts or intent approvals, deleting, spending, or the work Mac". Playbook 4b79e75c splits "spending": buying things (hardware, subscriptions, paid services) stays with the owner, and agent-run spend is reported, not asked about. So intent approvals (and model-binding amendments, which cannot be delegated: [docs/agent-usage.md](docs/agent-usage.md#delegated-approval)), deleting, buying things and the work Mac stay with the owner (playbook 8c758aa8). A run start does not: once the owner has approved the work and its plan, the driver starts its runs (a lead, or a worker commissioned to drive the run), or a delegated approval covers them (playbook f3404f07; the lean-change skill's "owner confirms first" start is its default, and the approved plan or that delegation stands in for the confirmation here). It stays with the owner only when the plan says a step needs the owner's word, the run is work the owner has not approved, or the run changes the approved plan or outcome. The driver's squash merge (Merge row above) and red-main steps (see [After merge](#after-merge-the-main-push-run)) need no further ask, and neither do the release steps under [Authorized release sequence](#authorized-release-sequence) (grants 19 and 46; playbook d9fa9f06). Creating a worktree or branch deletes nothing; it follows the recorded Git checkpoint decision above, the same as Git steps. Removing a worktree or branch is deleting: ask the owner before any removal and before any other destructive action; no grant covers them, except (1) a lean-change step's worktree and its branch once its work has merged to main and it has no uncommitted changes, after checking both (grant 51, from ask #1289, the owner's words "Yes, when merged and clean"; decision #3812), (2) the culprit-hunt worktrees (part of the method of [docs/culprit-hunt.md](docs/culprit-hunt.md) that coordinator playbook rule fab9b713 calls for, not an explicit grant; see [After merge](#after-merge-the-main-push-run)) (3) the release worktree that `scripts/release-after-merge.sh` creates and removes while cutting a release (docs/release-procedure.md; grant 19 and playbook d9fa9f06, not grant 46, whose exclusions include deleting), and (4) the release script's own cleanup under docs/release-procedure.md (grant 19, playbook d9fa9f06): the dist-plan file once checked, and the stash it prints, dropped only when `git stash show -p --include-untracked` (the contents, not just the file names) shows, once you have read them, that it holds nothing but the release script's own output; otherwise keep it and report it. The two checks for (1) are commands, and both must pass first. Merged to main: after `git fetch origin main`, either `git merge-base --is-ancestor <step-branch> origin/main` exits 0 (the step reached main by a merge commit or fast-forward), or, for a squash merge, which leaves no ancestor, `git merge-tree --write-tree origin/main <step-branch>` exits 0 and prints the same tree id as `git rev-parse 'origin/main^{tree}'` (merging the step into main would change nothing). A step that has only landed in the run's own branch, or in an unmerged PR, is not merged to main. Clean: `git -C <worktree> status --porcelain --ignored` prints nothing (`--ignored` matters: plain `status --porcelain` leaves out ignored files, such as a local config file or scratch output, and `git worktree remove` deletes them without a word; a worktree that lists any is not clean, so report it to the owner instead of removing it). Then remove it with `git worktree remove <worktree>` (never `--force`) and `git branch -D <step-branch>` (`-D`, because `-d` refuses a squash-merged branch; the merged check replaces its test). Everything else still goes to the owner: an unmerged or dirty step, any other worktree or branch, `--force`, and uncommitted work. A delegated approval ([Delegated approval](docs/agent-usage.md#delegated-approval)) is a lead's record of the owner's earlier approval or standing grant for a run's intent, including an accepted requirement change; it does not authorize Git or destructive steps. Git steps need the checkpoint decision above; destructive steps and deleting (branches, worktrees, uncommitted work) need the owner except the removals listed above, and a lead's checkpoint decision does not cover them. Ask the owner when no delegation covers an intent step, or the step adds, drops or changes an approved outcome. Before a commit, inspect `git diff --cached --name-status` and `git diff --cached`; this checkout has no tracked secret/runtime-artifact detection hook. Never commit secrets, machine-local provider TOML, run databases or captures. These markdown boundaries are advisory, not an enforcement mechanism; inspect staged contents and retain sensitive/runtime artifacts outside the checkout.

### Authorized release sequence

Before preparing, committing, pushing, dispatching or publishing a release, or regenerating release metadata, load [docs/release-procedure.md](docs/release-procedure.md). After a PR merges to main, first confirm that merge's push run is green (`gh run list --workflow ci.yml --branch main --event push --commit <merge sha>`; red means the red-main procedure and no release), because the script waits only on the push run of its own release-prep merge. Then run `scripts/release-after-merge.sh [--version X.Y.Z] [--notes FILE]` (`--notes` is needed only when a release-prep PR has to be made; see the script's usage): the owner's grant 19 ("cut the release when a PR merges to main") and playbook rule d9fa9f06 are the owner authorization for that run's steps, but the grant does not cover Loop Engine run starts.

The script's release-prep command (`RELEASE_PREPARE_CMD`, default `scripts/prepare-release.sh` on the host; no kgate wrapper is committed) and its `ci-main-status loop-engine` check and merge gate (`intent-review-check cartwmic/loop-engine <PR>`, found through `INTENT_REVIEW_CHECK`) before the release-prep merge are set out in [docs/release-procedure.md](docs/release-procedure.md#running-release-after-mergesh).
