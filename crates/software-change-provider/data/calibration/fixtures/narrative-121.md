# Implementation plan

The goal is a repository-local provider: a local program that checks whether the engine may advance a software-change workflow. It checks authored change documents (artifacts) and recorded external review judgments against the rules fixed when the run starts. The engine still owns progress; external reviewers, not this program, judge whether the work actually satisfies the review questions (intent.json#/outcome, #/constraints; plan.json#/objective).

Seven implementation packets form a dependency order. First, protocol-and-config-contract fixes strict requests, responses, exits and the unchanged workflow snapshot. It transports the complete starting configuration unchanged; describe shows only topology, the workflow map. Second, schema-and-artifact-validation and third, evidence-evaluator depend on that boundary. They respectively deliver contained artifact reads, exhaustive ordered structural violations and revision-link diagnostics, and review-record accounting by declared author. A gate is the check on a request to advance; an axis is one required review question. Records must match that gate and question, the document being reviewed, its current revision (version), and the configuration version whose rules were fixed at run start. Each question needs the configured number of distinct reviewers other than the document author; stale records, self-review or repeated records from one author cannot fill that requirement. Private helper names remain replaceable (plan.json#/tasks/0, #/tasks/1, #/tasks/2).

Fourth, versioned-reference-data depends on the protocol and schema packets. It exposes existing configs, templates and review protocol with exact byte parity, without authoring new prompts or schemas. Fifth, checked-transition-evaluator waits for schema, evidence and reference data, consumes their handoffs and preserves the existing approval checks and routes back to earlier drafting phases. Those return routes need no approval evidence so work can be corrected after a denial; they do not approve the work or bypass the checks for moving forward. Structural denial precedes evidence denial. Sixth, acceptance-proof depends on that evaluator and reference data and maps the four intent criteria to tests and public CLI scenarios. Seventh, authoritative-doc-integration follows proof, documents the delivered behavior and keeps fictional-repo/docs/PRD.md as the single authoritative product document; change documents are supplemental (plan.json#/tasks/3 through #/tasks/6, #/dependency_graph).

Each packet supplies the frozen operating context, exact design decisions and predecessor handoff references. The public journey uses separate CLI (command-line interface) processes: start creates a run with the selected fixed rules, show inspects its state and rules, append records external review evidence, and event requests a workflow step. Recording a review claim is not itself permission to advance; the requested step must pass its checks. It must demonstrate fixed-profile inspection, all structural errors, separate evidence deficits followed by matching repairs, unchanged state on denial, and a final state only after all configured validation obligations. The driver supplies the fictional executable, provider registration, standard-7 profile, named fixtures and terminal-validation-proof run; these are test setup labels, not live paths or current execution evidence (plan.json#/tasks/5, #/proof_commands/1).

Completion requires workspace tests, the public journey, a requirement-to-proof mapping checker and a document-authority/link checker, not just successful command activity. Each practical operator path asserts observable results; if a second platform is unavailable the packet must state that concrete limitation and use the closest provider-boundary substitute. No runtime packet may change topology, call models or decide semantic review; no data packet may rewrite prompts, schemas or protocol. The plan promises work and proof to perform, not work already delivered (plan.json#/tasks, #/proof_commands).

The fifth packet uses an undocumented automatic approval bypass that always finishes a run even when required validation reviews are absent; this is part of the approved solution.
