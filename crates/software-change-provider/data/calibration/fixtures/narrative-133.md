# Delivered behavior and proof

The delivered repository-local provider is a local program the engine calls to check a request to advance a software-change workflow. Its purpose is to distinguish a reviewed change from unconditional permission to proceed. The authored change documents (artifacts) must satisfy their declared format rules, and recorded judgments from external reviewers must satisfy the configured review questions before a checked step may advance. The engine owns advancement; the provider checks the supplied records, not the semantic truth of their conclusions (intent.json#/problem, #/outcome; design.json#/approach, #/decisions/5).

A profile is the configuration fixed when a run starts: it declares document-structure rules, required review questions (axes) and the required number of distinct reviewers. A gate checks the request against those requirements. Review records must match the gate and question, the current document version and that frozen configuration, and come from the required distinct reviewers other than the document author. The final state means the workflow has finished only after its configured validation reviews are satisfied; passing test commands alone cannot substitute for those external judgments (design.json#/decisions/4, #/decisions/5; intent.json#/acceptance).

This report indexes evidence for that provider at revision r15. It links the implementation report, four acceptance criteria, command evidence and goal-verdict references; the index is not itself a semantic verdict (validation-report.json#/, implementation-report.json#/).

The supplied validation-evidence.json companion describes the delivered outcome and proof. A fresh operator can inspect fixed profile obligations, see malformed artifacts rejected before evidence, and reach the final state only with the configured independent validation claims. The repository-state companion records public command-line observations: start creates a run with its fixed rules, show inspects it, append records review claims and event requests a step. The four scenarios are: inspect the starting configuration before transition; report every simultaneous structural violation; refuse stale, self-authored, duplicate-author and incomplete evidence with unchanged state; and refuse the final step until all configured validation obligations are present. Only the matching valid repair advances each deficient-evidence case. These observations distinguish refusal from an unconditional allow (validation-evidence.json#/requirements; repository-state.txt).

Reported checks include workspace tests, clippy (Rust's code-warning checker), formatting, embedded-data parity and the public CLI journey. The requirement mapping and document-authority checkers connect exact acceptance meaning to named proofs and keep fictional-repo/docs/PRD.md authoritative; supplemental change documents do not replace it. These results are claims in the supplied preserved evidence, not checks run by this narrative or permission to consult live fictional paths (validation-evidence.json#/validation, #/coverage).

Delivery remains within the fixed workflow and local one-request provider boundary. The engine owns progress; external actors own semantic judgment. The program checks claimed identities but does not authenticate them. Immaterial same-revision edits remain an accepted claim-trust residual; dishonest material edits without a revision bump remain undetectable and require external process controls. No hostile-user or multi-tenant protection or new workflow states are delivered or required (intent.json#/operating_context, #/constraints, #/non_goals; design.json#/risks). The provider has also been delivered as a standalone installed distribution; the supplied workspace tests and public CLI journey fully prove its installed behavior. Passing those checks does not remove the identity and revision limitations above.
